# PITFALLS

實際踩過的坑，按「症狀 → 原因 → 做法」記錄。每一條都來自這條產品線的真實事故，
不是理論上可能發生的事。開新站前讀一次，比事後除錯便宜。

---

## 1. `merchants.domain` 有兩個消費者，對格式的容忍度不同

**症狀**：商店查得到、目錄正常渲染、build 全綠，但線上**購物車完全不能用** ——
瀏覽器 console 全是 CORS 錯誤。preflight 回 204、`Vary: Origin`、
`Access-Control-Allow-Headers` 都在，就是**沒有 `Access-Control-Allow-Origin`**。

**原因**：commerce-workers 有兩支程式讀同一個 `merchants.domain` 欄位，容忍度不一樣。

| 消費者 | 對格式的處理 |
| --- | --- |
| `getMerchantByDomain()`（`lib/cache.ts`） | `domainLookupCandidates()` 展開六種形狀：裸 host / `https://` / `http://` × apex / www。任何一種都查得到。 |
| CORS 白名單（`lib/cors-allowlist.ts`） | `buildAllowedSet()` 對 DB 來源強制 `requireHttps`。**裸 host 直接被丟掉**，不進白名單。 |

所以一筆存成裸網域的 merchant 會落在「bootstrap 成功、CORS 靜默失敗」這個組合，
而 CORS 那側**不會產生任何錯誤訊息**，只是少一個 header。

**做法**：症狀是「查得到但打不通」時，兩支一起看，不要只驗 `merchant-by-domain`。
最快的判準是直接比對 preflight：

```bash
curl -s -i -X OPTIONS "$API/v1/storefront/cart" \
  -H "Origin: https://your-site.pages.dev" \
  -H "Access-Control-Request-Method: POST" | grep -i access-control-allow-origin
```

有回 ACAO 就在白名單裡，沒回就不在。再往下查 DB 那筆的三件事：
`domain` 有沒有 scheme、`is_active`、`is_test`。

**另外兩個相關事實**（同一支檔案的設計，不是 bug）：

- `is_test = true` 的商家**依設計**被排除在白名單外。測試站要放行請走
  `CORS_EXTRA_ORIGINS` 環境變數，不要去改 `is_test`。
- 比對是**完整 Origin 精確比對**，後綴比對已被刻意移除。所以 Cloudflare Pages
  每次部署的預覽網址（`<hash>.<project>.pages.dev`）**永遠不會**自動放行，
  只能逐一列進 `CORS_EXTRA_ORIGINS`。
- 白名單有 KV 快取（`cors:allowed:v1`，TTL 300 秒）。改完 DB 要等最多 5 分鐘，
  不要改完立刻重試就判定沒生效。

## 2. 本機的 storefront 副本可能落後 production

**症狀**：拿本機 repo 跟母版比對，得出「某功能在抽取時被砍掉了」或「上游根本沒有
這個功能」的結論 —— 然後被線上實際行為打臉。

**原因**：本機那份可能是幾週前的快照，或停在某個 feature branch。它是「某個時間點的
上游」，不是「現在的上游」。曾經據此判定「LOVISM 結帳沒有宅配地址欄位」，
但線上其實有 —— 該功能是在本機快照之後才進去的。

**做法**：要判斷 production 現在長什麼樣，**抓線上的 bundle**，不要只信本機 repo。

```bash
# 1. 頁面 HTML 先看 markup 在不在
curl -sL https://the-site.example/checkout | grep -o 'data-addr-city'

# 2. 追進 JS bundle 看實際送出的欄位
curl -sL https://the-site.example/checkout | grep -oE '/_astro/[A-Za-z0-9._-]+\.js'
# 入口 bundle 會 import 真正的邏輯檔，跟著 import 再抓一層
curl -s https://the-site.example/_astro/checkout.HASH.js | grep -o 'shipping_address'
```

本機 repo 只用來讀「為什麼這樣寫」（註解、commit message）。
「現在是不是這樣」一律以線上為準。

## 3. Cloudflare Pages normalises the trailing slash BEFORE it reads `_redirects`

**症狀**：在 `_redirects` 寫了 `/products  /  301`，部署後 `/products` 卻是 404 —— 規則像是完全沒被讀到。

**原因**：Pages 自己會先用 **308** 把 `/products` 正規化成 `/products/`，**然後才**拿 `/products/` 去比對 `_redirects`。你寫的是無斜線那一行，命中不了，於是掉進最後的 `/*  /404.html  404`。

**做法**：**兩種形式都寫**。先精確、後萬用，第一個命中者生效。

```
/products   /#catalogue  301
/products/  /#catalogue  301
```

**⚠️ 而且第一次驗證很可能騙到你。** `_headers` 給 HTML `s-maxage=600`，edge 會繼續餵**舊部署的頁面**長達十分鐘 —— 舊路徑看起來「還活著」（200），新規則看起來「沒生效」。兩者都是快取假象。驗證一定要繞過快取：

```bash
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  "https://your-site.pages.dev/products?cb=$RANDOM" -H "Cache-Control: no-cache"
```

看到 `301` 且 `redirect_url` 正確才算數。用 `curl -sL` 追到底、確認最終 URL 與狀態，比只看第一跳可靠。

### ⚠️ Workers 的順序是相反的，而且 `404` 規則會讓整包部署被拒絕

上面整段講的是 **Pages**。同一份 `dist/` 部署到 **Workers**（`wrangler deploy`
＋ `assets.directory`）時，行為在兩個地方相反，照上面的推理會推錯：

**一、順序相反。** Pages 先做 308 正規化、再讀 `_redirects`；Workers 的
`handleRedirects` 跑在 `getIntent` **之前** —— 重導規則先比對，路徑正規化後發生。
所以在 Workers 上，你寫的**無斜線那一行會直接命中**，不需要靠加上有斜線的版本救。

兩種形式都寫仍然是對的做法：那是同時滿足兩個 host 的寫法，在 Workers 上多寫的那行
不會有副作用。但「為什麼要寫兩行」的理由只在 Pages 成立 —— 別把它當成
Workers 也需要正規化。

**二、`404` 狀態碼在 Workers 上會讓 `wrangler deploy` 直接失敗。**
`dist/_redirects` 結尾這兩行：

```
/404  /404.html  404
/*    /404.html  404
```

- **Pages**：有效，但靠的是**未文件化的行為** —— Cloudflare 官方文件把 404 列在
  `_redirects` **不支援**的狀態碼裡（❌），實際上 Pages 會照做並送出自訂 404 頁。
  刪掉它們，Pages 就退回 Cloudflare 自己的 404，不是你的頁。
- **Workers**：**部署被拒絕**。不是忽略、不是死碼 —— 平台在上傳階段就擋下來：

```
✘ [ERROR] A request to the Cloudflare API (/accounts/…/workers/scripts/<name>) failed.

  Invalid _redirects configuration:
  Line 17: Valid status codes are 200, 301, 302 (default), 303, 307, or 308. Got 404.
  Line 18: Valid status codes are 200, 301, 302 (default), 303, 307, or 308. Got 404.
  [code: 100324]
```

**資產會先上傳成功，然後 script 上傳才失敗**，所以你會看到
`Uploaded 50 of 50 assets`、`✨ Success!`，幾秒之後才炸。事後
`wrangler deployments list` 是空的 —— **Worker 根本沒被建立**。

所以這兩行不是「在 Workers 上沒作用」，而是「有這兩行就完全不能用 Workers」。
一份 `dist/` 沒辦法同時滿足兩個 host。

**做法**：`brand/commerce.ts` 的 `deployTarget`（`'pages'` | `'workers'`，
不填等於 `'pages'`）決定 `scripts/build-deployment-files.mjs` 寫出什麼：

| deployTarget | `_redirects` 的 404 兩行 | 根目錄 `wrangler.jsonc` |
| --- | --- | --- |
| `pages`（預設） | 寫入 | **不寫**，舊的會被刪掉 |
| `workers` | 不寫 | 寫入，含 `not_found_handling` |

兩邊寫錯都是響的：pages 的產物餵給 `wrangler deploy` 會被拒絕，workers 的產物
根本沒有 `wrangler.jsonc` 可讀。換 host 是改這一行加重 build，不是手改 `dist/`。

Workers 上真正提供自訂 404 頁的是 `wrangler.jsonc` 裡的：

```jsonc
"assets": { "not_found_handling": "404-page" }
```

這個檔案由 `scripts/build-deployment-files.mjs` 產生（`name` 從
`identity.storageNamespace` 推導，避免兩站撞名互相覆蓋）。

### ⚠️ 這一條被改寫過，而「為什麼會寫錯」比結論更值得記

這一節原本寫的是「Workers 會**安靜地**把那兩行丟掉，其他規則照常生效」，
還特別強調「因為別的重導規則會動，你不會懷疑 404 那段」。**那是錯的**，
而且錯得很有信心 —— 它是一整段推理，不是一句順手寫下的猜測。

那個結論的來源是**文件 ＋ 讀 workerd 原始碼 ＋ 本機模擬**：
`PERMITTED_STATUS_CODES` 這個常數確實存在，parser 確實會丟棄不在裡面的規則，
本機跑起來也確實是那個行為。推理鏈每一環都對，結論卻不成立 ——
因為**真正擋下來的那一關在更前面，而且不在本機**：`wrangler deploy` 會把
`_redirects` 送到 Cloudflare API 做伺服器端驗證，在 parser 有機會「安靜地丟」之前
就整包退回。本機那個 parser 是對的，只是永遠輪不到它。

**教訓（這條比 404 本身通用）**：**本機模擬與真實部署是兩個不同的系統，
而部署路徑上的驗證關卡只存在於真實那一邊。** 讀原始碼能告訴你「執行時會怎樣」，
不能告訴你「上傳時會不會被收下」。任何關於部署行為的結論，
**在真的部署過一次之前都只是假設** —— 尤其是「這個錯誤會靜默發生」這種宣稱，
因為靜默正是最難從原始碼反證的性質。

同樣的懷疑要套用在這一節現在寫的東西上：下面的驗證步驟是**部署後**打真實網址，
不是本機 `wrangler dev`。

**驗證方式**：部署後打一個一定不存在的路徑，繞過快取，確認拿到的是 404 **而且**
body 裡有自訂頁的內容 —— 只看狀態碼不夠，空白頁也可能是 404：

```bash
curl -s "https://your-site.example/definitely-not-a-page?cb=$RANDOM" \
  -H "Cache-Control: no-cache" | grep -c "找不到頁面"
```

## 4. Bash heredoc 的 body 超過約 5KB 會在送達 bash 之前被截斷

**症狀**：用 `cat > file <<'EOF' … EOF` 寫一個比較大的檔，bash 直接回
``unexpected EOF while looking for matching `'``，而且檔案**完全沒有被建立**。
同樣的語法寫小一點的檔卻一路順暢，於是很容易誤判成「檔案被鎖住」或「權限有問題」。

**原因**：截斷發生在指令字串送達 bash **之前**，不是 heredoc 語法寫錯。那一刀落在
heredoc body 中間，`<<'EOF'` 的引號因此永遠不會閉合，bash 在**解析階段**就放棄整條指令。

實測邊界：一輪作業裡成功的 heredoc 全部 ≤ 5,282 bytes，8,395 和 8,600 bytes 兩次都失敗。
拿一段**只有數字、完全不含引號**的 8.6KB payload 可以穩定重現同一個錯誤 —— 所以與引號
奇偶、跳脫字元、CJK 都無關，唯一的變因是長度。

**做法**：heredoc body 控制在 5KB 以下；超過就改用 Read + Write 工具寫檔。

**不要用「先寫暫存檔、再 cp 過去」繞道。** 繞道會成功，但會讓根因隱形 —— 下一個人只會
看到一個沒有理由的暫存目錄，然後在下一個大檔上再踩一次同樣的坑。

**一個安慰**：這是響的失敗，不是啞的。引號 heredoc 被截斷必然導致解析失敗，bash 會拒跑，
不會寫出半個檔案，所以不需要回頭逐一檢查先前寫過的檔有沒有被寫壞。

## 5. 外部 `<img>` 載入的 SVG 解不了 `currentColor`

**症狀**：一組線條圖示在設計稿上是品牌金，換站換了 `--color-cta` 之後**還是舊的金**。
`audit:color` 全綠，因為它只掃 `src/`，而顏色是烘在 `brand/assets/**.svg` 檔案裡的。

**原因**：`<img src="icon.svg">` 會把那支 SVG 當成**獨立文件**載入。它沒有父層可繼承，
所以 `currentColor` 解不到任何東西（實際上會退成黑色），CSS 也碰不到它的內部節點 ——
`.icon { color: … }`、`.icon path { fill: … }` 通通無效。唯一會生效的顏色，
就是檔案自己寫死的那個。

**做法**：**檔案只給形狀，token 給顏色**。用遮罩，不要用 `<img>`：

```astro
<span class="link-ic" style={`--glyph: url('${icon}')`} aria-hidden="true"></span>
```

```css
.link-ic {
  width: 30px; height: 30px;
  background: var(--color-cta);          /* ← 顏色來自色票 */
  -webkit-mask: var(--glyph) center / contain no-repeat;
  mask: var(--glyph) center / contain no-repeat;   /* ← 檔案只提供形狀 */
}
```

SVG 那側同步改成 `stroke="currentColor"` / `fill="currentColor"`。遮罩只看 alpha，
不看顏色，所以寫什麼都不影響渲染 —— 但寫死一個顏色會在別人哪天改用 `<img>` 時復活，
所以不要留。

**兩個例外**（本來就不該跟著換膚）：

- **第三方標誌**：LINE 綠是 LINE 的，不是這家店的。
- **圖片佔位圖**：它替代的是照片，照片本來就有顏色。

這兩類要在 `brand/assets/manifest.json → colourLiterals` 具名宣告才放行。
`audit:color` 第二輪掃 `brand/assets/**/*.svg` 是**預設拒絕**：每個 `fill` / `stroke` /
`stop-color` 只准是 `currentColor`、`none`、`inherit`、`transparent`、`var(…)` 或
`url(#…)`。刻意不是 hex grep —— `fill="white"` 也是寫死的顏色，抓 `#` 會放它過去。

## 6. `/assets/*` 不是內容定址，所以不能宣稱 `immutable`

**症狀**：換掉 `brand/assets/home/hero.jpg` 的照片、build 綠、deploy 成功，
線上**還是舊圖**。或者相反：從 `brand/assets/` 刪掉的檔案，部署裡明明沒有它，
線上仍回 `200`。改動的人自己看不到問題，因為他當下打到的邊緣節點剛好是冷的。

**原因**：`immutable` 是一句承諾——「這個 URL 的位元組永遠不會變，不必再問我」。
`/_astro/*` 守得住：Astro 把內容雜湊放進檔名，位元組變了、URL 就變了。
`brand/assets/` 的檔名是**人取的**，`hero.jpg` 在換照片之後還是 `hero.jpg`。
同一個 URL、不同的位元組，正是 `immutable` 說不會發生的那件事。

實際踩過的兩種：

- 一支從 `brand/assets/` 刪掉的圖示，部署完成 **90 分鐘後**仍回 `200`，
  `CF-Cache-Status: HIT`、`Age: 5777`。
- 換過的 hero 會在任何持有舊副本的邊緣節點繼續送舊照片，最長一年。

第二種才是危險的那個。**檔案不見了遲早有人回報，檔案過期只是靜靜地不是新版。**

**目前做法**：`/assets/*` 給一小時，之後靠 ETag 重新驗證；`immutable` 只留給
`/_astro/*`。夠一個 session 只下載一次 hero，也夠讓「換圖」是一次部署而不是一年。

```
/assets/*
  ! Cache-Control
  Cache-Control: public, max-age=3600, s-maxage=3600, must-revalidate
```

**還沒做（backlog）**：在 `scripts/sync-brand-assets.mjs` 同步時對 brand 資產做
**內容定址**——把內容雜湊寫進檔名、產生一份 map，讓 `brand/` 那側仍用
`hero.jpg` 這種人看得懂的名字引用。做完之後 `/assets/*` 才**真的**可以是
`immutable`，而且換圖天生不必等快取。上面那個一小時是止血，不是解法。

**運維上的陷阱**：`*.pages.dev` 的快取**你清不掉**。cache purge 是 zone 層級的操作，
而 `pages.dev` 這個 zone 屬於 Cloudflare，不在你的帳號底下——沒有自訂網域就沒有
可以 purge 的 zone。已經被舊 header 快取起來的條目，只能等它過期，
或是**換檔名**（換 URL 等於換一份快取條目）。所以這件事的成本是預防性的：
`immutable` 一旦送出去就收不回來。

## 7. 量 hero 對比之前，要先算出文案落在圖的哪一塊

**症狀**：換了一張新的 hero 照片，對它量了 WCAG 對比、數字很漂亮、`audit:color`
全綠，上線之後標題還是讀不清楚。或者相反 —— 一張其實可用的圖被一個難看的數字擋掉。
兩種都是**量錯區域**，不是量錯公式。

**原因**：`audit:color` 量的是**色票**（宣告值對宣告值），它看不到照片。而人對照片
量對比時最容易做的兩件事都會騙人：

1. **量整張圖**。文案只落在圖的一小塊 —— landing 版是左側 520px 寬的一柱。
   對整張圖取平均，等於拿天空的亮度去替標題背書。
2. **忘記 `object-fit: cover`**。`.home-hero img` 是 `cover` + `object-position: center`，
   所以瀏覽器會先把圖**裁切並縮放**才貼上去。CSS 版位上的那塊矩形，對應到
   **原始圖檔**是另一塊矩形。直接拿 CSS 座標去原圖上取樣，量到的是隔壁。

還有第三件事：**對比在照片上是一個分布，不是一個數字**。同一張圖可以「平均 9:1」
而仍有 5% 的文字面積低於 AA —— 而那 5% 通常落在明體標題的細筆畫上，
眼睛看到的比百分比聽起來嚴重得多。

**做法**：三步，順序不能換。

**第一步 — 先算版位（CSS 座標）。** 常數全部在 repo 裡，不要用目測：

| 值 | 來源 |
| --- | --- |
| hero 高 `H` | `.home-hero { min-height: min(720px, 100vh) }` |
| 容器寬 `Cw` | `.container { width: min(100% - 48px, var(--container)) }`，`--container: 1200px`（≤768px 改 32px 邊距、≤640px 改 `--mobile-padding: 16px`） |
| 容器左緣 `Cx` | `(Vw - Cw) / 2`（`margin-inline: auto`） |
| 文案柱寬 | `.hero-copy > * { max-width: 520px }`（HomeMultipage 是 460px），靠左 |
| 垂直位置 | `.home-hero { display: grid; align-items: center }` → 文案區塊垂直置中 |

所以在 1440×900 的視窗上：`Cw = min(1392, 1200) = 1200`、`Cx = 120`、
文案矩形 x ∈ [120, 640]，y 以 `H/2` 為中心、上下各半個文案區塊高
（eyebrow + h1 + 內文 + 按鈕，約 260–300px）。

**第二步 — 把矩形映射到原圖。** `cover` 的縮放係數是
`s = max(Vw / Iw, H / Ih)`，置中裁切的位移是
`ox = (Iw * s - Vw) / 2`、`oy = (Ih * s - H) / 2`。原圖座標 =
`((x + ox) / s, (y + oy) / s)`。**做完這一步再取樣。**

**第三步 — 量分布，不要量平均。** 對矩形內每個像素算它與文字色的 WCAG 對比，
然後看兩個數字：

- **低於 4.5:1 的面積百分比** —— 這是「有多少字踩在爛地方」。
- **5th percentile** —— 這是「最糟的那批像素有多糟」。平均值會把它藏起來。

**⚠️ 第三步半 — 百分比不及格之後，先問「那些像素在字上嗎」。**

矩形是 `.hero-copy` **子元素的聯集**，不是墨水的形狀。文案靠左對齊，而 `max-width`
是 520px（手機是容器寬）—— 所以一個六字標題只佔掉矩形的三分之一，**右邊那半塊永遠
不會有字**。整塊 rect 的百分比會把那半塊一起算進去，於是**虛高**。

實際踩到的一次：手機 scrim 量到 **8.04% 未達 AA**，看起來該補救。改成**逐字**量
（每個字自己的 rect 對照它背後的地面）之後，標題與內文 **24 個字全部 0%**。5,523 個
失敗像素裡只有 18 個落在墨水的欄位範圍內，而且沒有一個在任何字的框裡 —— 它們全在
文字右邊的抱枕與畫框上。**那 8% 不是可讀性問題，是量測方法的形狀。**

代價是真的：當時差點為此把 scrim 加濃。模擬到 45%/85% 時 rect 降到 2.70%、60%/95%
降到 0.07%，而逐字分數**從頭到尾都是 0/24** —— 根本沒有字需要被救。加濃唯一買到的是
一張更白的照片（scrim 是 `--color-surface`），到 60% 時窗戶與抱枕都不見了。

所以順序是：**先看百分比，再看那些像素落在哪裡。** 逐字量測才是可讀性的真相，
整塊 rect 的百分比只是入口。

```js
// 每個字自己的 rect —— 用 Range 逐字取，不要用整段的 boundingRect
const range = document.createRange();
range.setStart(node, i); range.setEnd(node, i + 1);
const r = range.getBoundingClientRect();   // 這塊裡有幾成未達 AA？
```

**但逐字乾淨有一個附帶條件：它是「這句話這個長度」的結論，不是「這張圖」的結論。**
上面那次，墨水右緣在 x=194、第一個失敗欄在 x=192 —— **餘裕 0px**。標題再長一個字就
踩進去，0/24 立刻不成立。逐字量測過關的話，把**當下的文案長度**一起記進
`brand/copy.ts`，並註明換文案要重量。

---

量完之後，`brand/copy.ts → hero.copyGround` 有三個答案，而**量測結果決定選哪個**：

| 量到 | 選 | 為什麼 |
| --- | --- | --- |
| 低於 AA 的面積 **0.00%** | `'none'` | 照片自己撐得住，別在它上面加東西。這個值是一句**宣稱**：宣稱有人量過。 |
| 只是勉強（幾個 % 以內） | `'scrim'` | 便宜，留得住照片。留意它前 26% 是實色 `--color-surface`，某些構圖會讀成「照片少了左邊那塊」。 |
| 明顯不過，或不想再賭下一張圖 | `'panel'` | 面板把「分布」換成一組 `audit:color` 已經在檢查的**宣告色對**（`--color-on-dark` on `--cta-dark`），從此不管背後是哪張照片。 |

欄位留空 = 讓 `tone` 決定（light 給 scrim、dark 給不加），也就是這個欄位存在之前的行為。
**寫 `'none'` 跟不寫是兩件事**：不寫是還沒想過，寫了是量過。

**桌機與手機是兩個答案，因為是兩張照片。** `hero.mobileCopyGround` 管
760px 以下，`hero.copyGround` 管 760px 以上。這不是為了方便：直式裁切是**另一張照片**，
文案落在它的另一組像素上，量出來可以完全不同。實測過的兩間店，
橫式裁切 0.00% 未達 AA、同一支 hero 的直式裁切分別是 **22.36%** 與 **41.19%**。
一個欄位管兩邊的話，只能在「手機讀不了」跟「桌機背一塊它不需要的面板」之間挑一個。

`mobileCopyGround` **不填 = 繼承 `copyGround`**，不是視為 `'none'`。
理由是：把不填當成不加，會讓每一間既有店家的**手機** hero 靜靜掉掉它的 scrim ——
而手機正是量測結果顯示最需要襯底的那一面。繼承的話，這個欄位加進來的那天，
沒有任何一間店的畫面變過。

**一個接縫要知道**：`<picture>` 換圖在 **720px**，而 ground 換手在 **760px**，
所以 721–760px 這 40px 是「橫式照片 ＋ 手機的 ground」。
往常用的方向沒問題（面板是宣告色對，蓋在哪張照片上都安全），
但如果有人設 `copyGround: 'panel'` 配 `mobileCopyGround: 'none'`，那 40px 就沒有保護。
要嘛連那一段一起量，要嘛不要把兩個答案排成那個順序。

**還沒做（backlog）**：`tone` 沒有跟著拆成 `mobileTone`。

這個不對稱是**刻意留著的**，不是漏掉。`copyGround` 拆兩層有實測撐腰 —— 同一支 hero
的直式裁切量到 22.36% 與 41.19%、橫式 0.00%，兩邊答案不同。`tone` 沒有這種證據：
實際量過的那張（白色高調臥室，Sommeil 的 hero）在 `ground: none` 下，深字桌機
**19.06%**、手機 **19.25%** —— 差 0.19 個百分點，兩個裁切在「該用哪種墨色」上幾乎
完全同意。同一張圖的淺字是 83.21% / 84.02%，也是兩邊一致地不及格。那張圖上真正
分歧的是 **ground**（scrim 桌機 0.00%、手機 8.23%），而那個維度已經拆過了。

**觸發條件**：遇到一張圖，橫式與直式的**墨色答案分歧** —— 直式裁切把文案落點從亮部
換到暗部，於是一邊該用深字、另一邊該用淺字 —— 那就是證據，屆時再加。在那之前加它
是猜，而且要一併處理上面那個接縫：`<picture>` 在 720px 換圖、ground 在 760px 換手，
tone 若也在 760px 換手，721–760px 那 40px 會是「橫式照片 ＋ 手機的 tone」。

**桌機與手機要各量一次。** `<picture>` 在 720px 以下換成 `hero.mobileImage`，
直式裁切的構圖跟橫式完全不同，一張過不代表另一張過。

**手邊有無頭瀏覽器的話，第一、二步可以外包給它** —— 而且應該外包。
用 Playwright 開 `dist/`（起一個小 static server，`file://` 解不到 `/assets/`），
拿 `.hero-copy` 每個子元素的 `getBoundingClientRect()` 取聯集，
再把 **`.hero-copy > *`** 設成 `visibility: hidden`（**只隱藏、不移除**，版位要留著）
截那塊矩形。截出來已經是渲染後的裝置像素、`cover` 裁切都算好了，
第二步整個消失，也沒有「算錯版位」的空間。剩下的就是對每個像素套 WCAG 公式。

**⚠️ 藏的是子元素，不是 `.hero-copy` 本身。** 這條是踩出來的：
面板畫在 `.hero-copy::before`，而 `visibility: hidden` 會**連自己的偽元素一起藏掉**。
藏錯層級的話，你量到的是面板後面的照片 —— 開了面板跟沒開會量出**一模一樣**的數字，
而那個「沒有改善」看起來完全像是面板無效。實際踩到時是 41.19% 開關前後不動，
改藏子元素之後同一份 build 量到 0.00%。

順帶一提，這也是面板量起來會長什麼樣：面板是一組**宣告色對**，
所以整塊區域同一個值 —— `min` 會等於 `5th pct` 等於平均。
量到一個完全沒有分布的分布，就是面板確實蓋住了。

驗算一下值不值得：在 1440×900 上，瀏覽器回報的矩形是 **520×244 @ (120, 322)** ——
`Cx = (1440 - 1200) / 2 = 120`、寬 520，跟上表推的完全一致。
手機 390×844 是 **358×229 @ (16, 79)**，`358 = 390 - 16 × 2`，也對得上。
兩邊互相驗證之後，你才知道自己量的是那塊文字，不是隔壁的天空。

**為什麼這條是文件而不是腳本**：量測需要**解碼點陣圖**。`scripts/` 是不帶相依套件
的純 Node（`brand-facts.mjs` 用文字掃描讀 `brand/` 就是同一個約束），為了一張
hero 圖引進一個 JPEG 解碼器，會把三道稽核從「clone 完就能跑」變成「先裝東西」。
上面第一、二步 —— 也就是真正會量錯的那兩步 —— 是**算術**，寫下來就夠了；
第三步任何有 canvas 或 Pillow 的環境十行就能寫。

**面板本身的兩個坑**（都踩過）：

- 面板必須畫在 `::before`，不能直接給 `.hero-copy` 背景加寬度。`.hero-copy` 同時
  帶著 `.container`，它自己 `margin-inline: auto`；一給寬度，它就把自己置中到
  hero 正中央，文案離開頁面其他區塊共用的左緣。
- 面板上的按鈕要給**淺色邊**。木色 CTA 貼深色面板實測 1.41:1，
  WCAG 對 UI 元件邊界要 3:1 —— 邊界看不見的按鈕不是按鈕。
  `--color-on-dark` 已經被稽核過，拿它當 `border-color` 不必動 CTA 的顏色。

## 8. `mobileCopyGround: 'panel'` 在窄螢幕會變成橫貫色帶

**症狀**：對比量測漂亮得不能再漂亮 —— 面板是一組宣告色對，逐字量出來
**平坦的 6.19:1**，沒有分布、沒有最差像素、`audit:color` 全綠 —— 但畫面看起來壞掉。
照片被切成上中下三截：上面一條、色帶、下面一條。

**原因**：面板是**依文案尺寸畫的實色塊**，而文案在兩個寬度上是兩種東西。
桌機的文案是 520px 的一柱，面板佔畫面四分之一，看起來像一個**裝置**；
手機的文案是滿版寬 —— 容器的邊距是它唯一沒佔到的地方 ——
面板於是橫貫整個畫面，變成一條**有硬邊的帶子**，而那兩條硬邊把照片切斷。

同一個宣告，兩種結果。`copyGround` 與 `mobileCopyGround` 拆成兩個欄位是為了讓
**量測結果**可以不同（#7 的最後一段），但這一條是另一回事：即使兩邊量測結果相同，
面板這個**形狀**在窄螢幕上也不對。

**為什麼量測抓不到**：#7 把「量到一個完全沒有分布的分布」寫成**面板生效的證據**。
那句話沒有錯，但它在窄螢幕上同時也是**照片被切斷的證據** —— 一塊區域裡每個像素
都是同一個值，意思就是那塊區域裡沒有照片了。同一個數字，兩種讀法，而量測只會給你
其中一種。

**對比是約束，不是目標。** 面板永遠會贏得對比這一局，所以「哪個 ground 量得最好」
不是要問的問題；要問的是「在數字過關的選項裡，哪一個沒有把照片弄壞」。

**做法**：手機優先 scrim，而且**窄螢幕要換的是形狀，不是深度**。

側向漸層在 390px 只蓋得到半邊。文案是滿版寬的，所以每一行的另外半邊站在裸照片上 ——
實測那半邊是 **1.00:1**。那不是「對比低」，是**沒有底**。而加濃解決不了它：
再濃的側向漸層，蓋不到的那半邊還是蓋不到。

改成**由上而下、`--scrim-end` 走到 100%**。這樣它是一層蓋滿整張照片的漸層，
**裡面沒有任何一條邊**，也就沒有半邊可以漏掉。

```css
/* 這是每一間店自己的 HomeLanding.astro 該寫的，不是母版的預設。
   母版改預設會讓每一間既有店家的手機 hero 靜靜換一次形狀。 */
@media (max-width: 760px) {
  .home-hero--mground-scrim {
    --scrim-angle: 180deg;   /* 0deg 是由下而上 */
    --scrim-solid: 55%;
    --scrim-end: 100%;
    --scrim-color: color-mix(in srgb, var(--scrim-tint) 85%, transparent);
  }
}
```

**由上而下還是由下而上，是這張照片的答案，不是預設。** 兩件事一起決定：
**文案哪一行最弱**，以及**照片哪一端最不值錢**。TrailNest 兩者都指向上方
（eyebrow 在最上、上方是暗林），所以往下走沒有懸念。Sommeil 兩者**打架** ——
最弱的是內文第二行（在下），最不值錢的是天花板與牆（在上）—— 於是兩個方向都量了：
往下 5.41:1、往上 5.43:1，**分數等於沒有差別**，就由照片決定。往上會讓實色區落在
床與抱枕上，一間賣寢具的店的 hero 會沒有寢具。

**順序**（踩過才排出來的）：

1. **加濃 scrim** —— 最便宜，而且通常就夠了。
2. **重切直式裁切** —— 換的是文案落在哪些像素上，比換照片便宜得多。
3. **換照片**。

`panel` 留給極端情況：手機用它，就要接受畫面上會有兩條硬邊。

**附帶事實 —— 實色區只要覆蓋到最弱的那一行就夠，多的長度是白白蓋掉照片。**

TrailNest 實測 40% 與 55% 量出**完全相同**的數字，因為 eyebrow 整個落在實色區裡，
兩者對它而言沒有分別；中間那十個百分點只換到一張更白的照片。
Sommeil 是同一件事的另一半：它沒有 eyebrow，所以綁住結果的是**內文的最後一行** ——
最低的那一行，也就是掉進漸層最深處的那一行。掃出來是

| `--scrim-solid` | 內文逐字 | 最差 |
| --- | --- | --- |
| 48% | 18 字中 5 字未達 AA | 4.31:1 |
| 50% | 0/18 | 4.63:1 |
| 52% | 0/18 | 5.02:1 |
| **55%** | **0/18** | **5.41:1** |
| 60% / 65% / 70% | 0/18 | 5.41:1（**三個一模一樣**） |

55% 是那條平台的起點 —— **拿到滿分的最短的那個值**。再長下去，逐字分數一個字都不會
變，只是照片一路被蓋掉。所以掃的時候要往**短**的方向逼，不是往長的方向加保險。

**⚠️ 還有一個 #7 沒寫到的陷阱：整塊 rect 的百分比只用了一種墨色。**

`.hero-copy` 裡不只一種墨 —— 標題是 `--text-primary`，內文是 `--text-secondary`，
後者比較淺。整塊 rect 的數字只能挑一個墨色去算（實作上是第一個，也就是標題的），
於是**內文被標題的墨色背書**。Sommeil 在 `--scrim-solid: 35%` 時，
整塊 rect 量到 **0.00% 未達 AA**，而同一份 build 逐字量，**內文 18 字裡有 7 字未達**。

rect 說乾淨、字其實不乾淨 —— 這比 #7 講的「rect 虛高」更難發現，因為它是往**好**的
方向錯。**逐字量測，而且每個字要對它自己的墨色量。**

**一筆實際的改動**（Sommeil，同一張照片、同一段文案，只換形狀）：

| | 側向（母版預設） | 由上而下走到底 |
| --- | --- | --- |
| 整塊 rect | 8.04% 未達 AA，min **1.00** | **0.00%**，min 6.44 |
| 標題逐字 | 0/6，最差 11.16 | 0/6，最差 11.87 |
| 內文逐字 | 0/18，最差 **4.63** | 0/18，最差 **5.41** |
| 墨的右緣 vs 第一個失敗欄 | 194 vs 192 —— **餘裕是負的** | 沒有失敗欄 |

逐字分數**兩邊都是 0/24**，所以這件事光看「過不過」是看不出來的。改動買到的是
**#7 最後那個警告的消失**：舊的形狀下，標題再長一個字就踩進失敗區；新的形狀下，
整塊區域裡沒有失敗區可以踩。

桌機在整個過程中**一個數字都沒有動**（0.00%、0/24、最差 7.42:1）——
因為這條規則整個活在 `@media (max-width: 760px)` 裡。要的就是這樣：
這是一個關於**窄螢幕**的修正，不是關於這張照片的修正。

## 9. 遮罩的掃描結果，是「文案落點」與「文案顏色」兩者的函數

**一句話**：`--scrim-solid` 那個百分比不是關於照片的，是關於
**「這些字、這個顏色、落在照片的這一塊」**。這三件事任何一件動了，
先前掃出來的結果就**作廢**，而且**沒有任何一道稽核會說話**。

已經發生過兩次，各動了其中一半：

| | 動了什麼 | 結果 | 稽核 |
| --- | --- | --- | --- |
| **落點** | hero 字級 28px → 36px，文案區塊撐高 | 手機內文 5.57:1 → **4.85:1**（餘裕 1.07 → **0.35**） | 全綠 |
| **墨色** | 副標從 `--color-on-dark` 換成暖金 `--color-on-dark-accent` | 7.36:1 → **3.98:1**（**掉出 AA**） | 全綠 |

第二列值得停下來看：那是一個**已經掉出 AA** 的結果，四道稽核照樣全綠。
原因在 #10 —— 稽核量的是**宣告的色對**，而副標的實際背景是照片，不是任何一個 token。
`--color-on-dark-accent` 對 `--cta-dark` 是合格的，稽核量的就是那一對；
它從來沒有量過「暖金落在那張照片的那一塊」。

所以 #9 的完整形狀是：

> 遮罩 = f(文案落在哪, 文案是什麼顏色)
> 任一半移動 → 先前的逐字量測作廢 → 重掃。

### 9a. 落點那一半

**原因**：scrim 的 `--scrim-solid` 是**掃出來的**，而掃的時候有一個沒有寫下來的
前提 —— **當時的文案矩形**。#8 說「實色區只要覆蓋到最弱的那一行就夠」，
那個「最弱的那一行」在垂直方向的位置，是由**整個文案區塊的高度**決定的：

```
.home-hero { display: grid; align-items: center; }   ← 文案區塊垂直置中
```

置中的意思是，區塊**變高就往兩邊長**。標題大一級，區塊高 123px → 178px，
最下面那一行就往下掉了約 27px —— 而 scrim 的實色區還停在原本掃出來的百分比。
那一行於是從實色區裡**掉進漸層裡**。

實例（TrailNest，`clamp(28px, 3vw, 40px)` → `clamp(36px, 3.75vw, 54px)`）：

| 390px 手機 | 舊字級 28px | 新字級 36px |
| --- | --- | --- |
| 文案矩形高 | 123px | 178px |
| 內文逐字 | 0/13，最差 **5.57:1** | 0/13，最差 **4.85:1** |
| 距離 AA 的餘裕 | 1.07 | **0.35** |

沒有掉出 AA，所以**沒有任何一道稽核會說話**。餘裕從 1.07 掉到 0.35 是這次唯一的
訊號，而它只有逐字量測看得到。

**⚠️ 方向不一定是變糟。** 同一次改動裡，TrailNest 的**桌機** eyebrow
從 5.39:1 升到 6.51:1 —— 一樣是區塊變高、一樣是往兩邊長，但 eyebrow 是往**上**長，
在那張照片上正好離開了亮部。所以這不是「字放大會讓對比變差」，是
**「字級改變了文案落在照片上的位置」**，往哪個方向要看照片。

### 9b. 墨色那一半

同一個矩形、同一張照片，**只換了字的顏色**，先前的掃描一樣作廢。

實例：hero 副標從 `--color-on-dark`（近白）換成 `--color-on-dark-accent`（暖金），
理由是視覺上要把標題與副標用**色溫**分開而不是只靠字級 —— 這是對的設計決定。
代價是那一段文字對背後照片的對比從 **7.36:1 掉到 3.98:1**。

值得注意的是**方向的不對稱**：往深色換通常在深底上變糟、在淺底上變好，
但照片不是單一底色，它同時有亮部和暗部。所以「換個顏色會變好還是變壞」
**不能從 token 對 token 的比值推**，只能重掃。

而且這一半比落點那一半更容易漏掉，因為改顏色感覺上是「調色盤的事」，
而調色盤有稽核 —— 稽核也真的全綠了。它綠得完全正確：
它量的那一對確實合格。它只是沒有量到那段字實際站在哪。

**做法**：把「字級」「墨色」和「ground 的掃描結果」當成**同一個決定的三分之一**。

1. 改字級**或改任何落在照片上的墨色**之後，**每一站的每一個寬度都要重跑逐字量測**。
   不是抽查一站 —— 五站的標題長度不同，矩形長高的幅度就不同
   （這次是 +5 到 +140px 不等）。
2. 掃 scrim 的時候，**把當時的文案矩形高度一起記進註解**。
   `brand/copy.ts` 已經在記文案長度（#7 的最後一段），矩形高度是同一類事實：
   它是那個百分比成立的前提，不寫下來，下一個人就會以為那個數字是關於照片的。
3. 餘裕**低於 0.5** 就當成訊號。它還是綠的，但它已經沒有下一次的空間了。

**為什麼不乾脆讓 scrim 跟著文案走**：試過這個念頭，結論是不要。
scrim 是畫在 `.home-hero::after` 上、覆蓋整個 hero 的漸層，它的百分比是
**hero 高度的百分比**，不是文案的。要它跟著文案，就得把漸層改成畫在文案區塊上 ——
那就變回 #8 那條「面板在窄螢幕會變成橫貫色帶」的形狀。
**漸層蓋整張圖是它之所以沒有硬邊的原因**，這個性質比自動對齊值錢。

**還有一件事順帶被證明了**：孤字（一行只剩一個字）**沒有**「安全字級」。
`clamp()` 在每個視窗寬解出不同的值，所以它會**掃過兩端之間的每一個字級**。
360–1600px 每 20px 掃一次，五站之中：

- 現行的 `clamp(28px, 3vw, 40px)` 已經在 460px 與 1100–1160px 讓 Pawfect 掉「久」
- `clamp(32px, 3.6vw, 48px)` 在 **390px** 與 **1240–1600px** 讓 TrailNest 掉「能」
- `clamp(36px, 4.2vw, 56px)` 在 **1300–1600px** 讓 LEMONE 掉「常」

所以要問的不是「哪個字級沒有孤字」，是
**「哪個字級在最常用的那幾個視窗寬是乾淨的」**。
選定的 `clamp(36px, 3.75vw, 54px)` 是「1440 與 390 都乾淨」的最大值，
它在 1200–1300px 還是會讓 TrailNest 掉「能」—— 那是知情之後接受的，
不是沒看見。**而且這是關於當下這五句標題的結論**：改一個字，整件事要重來。

## 10. 稽核管「宣告的色對」，量測管「落在照片上的實際像素」，兩者永遠有縫

**一句話**：`audit:color` 讀的是 `brand/identity.ts` 裡兩個 token 的比值。
文字實際站的地方是**一張照片**，照片不是任何一個 token。
這條縫**不是 bug，是定義上的**，補不起來 —— 能做的只有知道它在哪裡。

**症狀**：四道稽核全綠、build 全綠、`palette contrast verified` 印出上百對，
然後把 hero 放大逐字量，**0.14% 的墨水低於 3:1**。

**RideForm 實例**：hero 文案落在照片上，逐字量測（每個字元自己的矩形對背後的實際像素）
發現 0.14% 的墨水面積低於 3:1。同一時刻：

- `audit:brand` 綠
- `audit:color` 綠 —— 它量的是 `--color-on-dark` 對 `--cta-dark`，那一對確實合格
- `audit:template` 綠
- `node --test` 綠

四道全綠，因為**沒有一道在問那個問題**。稽核能回答
「這個 token 站在那個 token 上合不合格」，不能回答
「這些字站在這張照片上合不合格」，而後者是使用者真正看到的東西。

**為什麼不把量測做成稽核**：試過這個念頭，結論是不要。逐字量測需要
把頁面真的算繪出來（真實字體、真實斷行、真實圖片解碼），
那是一個瀏覽器等級的相依，跑一次以分鐘計，而且結果會隨字體載入時序抖動。
把它塞進 `npm test` 會得到一道**偶爾紅、大家學會忽略**的稽核，
那比沒有更糟。

**做法**：把兩者當成**不同工具**，不是同一件事的粗細兩版。

1. **稽核跑每一次 commit**，它保證的是「調色盤內部自洽」。
2. **量測跑在改動 hero 的時候**（#9 的兩個觸發條件：落點動了、墨色動了），
   它保證的是「這一張照片上這一段字讀得到」。
3. **稽核綠不是量測綠的證據**，反過來也不是。看到「全綠」要先問
   *哪一道稽核在問我關心的那個問題* —— 如果一道都沒有，那個「全綠」
   對這個問題**沒有攜帶任何資訊**。

`docs/PITFALLS.md` #7 講的是怎麼算出文案落在圖的哪一塊；
#9 講的是什麼會讓那個結果作廢；這一條講的是
**為什麼稽核從頭到尾都不會替你發現這件事**。

## 11. 狀態碼與 `CF-Cache-Status` 回答不了「線上現在是哪一版」

**一句話**：`200` 告訴你有東西回來了，`CF-Cache-Status: MISS` 告訴你這一次不是快取。
兩者都**不是**「線上跑的是我剛推的那一版」的證據。
唯一的判準是**線上 HTML 與本機 `dist/` 逐位元比對**。

**咬人的兩個方向**（兩個都發生過，而且長得完全不一樣）：

**方向一：新規則看起來沒生效。**
改了 `_headers` / `_redirects`，部署完 curl 一下，行為還是舊的。
直覺是「快取還沒過」，於是等、於是 purge、於是加 `?v=2`。
真正的原因可能是那個檔**根本沒被平台接受**（見 #3：Workers 直接拒收帶 404 的
`_redirects`，整個 deploy 失敗但 assets 已經上傳完成，看起來像成功）。
`CF-Cache-Status: MISS` 在這個情境下是**真的** —— 它確實不是快取，
它是**新鮮地送出了舊的東西**。

**方向二：新內容看起來沒上去。**
反過來，HTML 明明是新的，但某個 `/_astro/*.js` 還是舊的雜湊。
狀態碼一樣是 200，`CF-Cache-Status` 一樣可以是 MISS。

**為什麼這兩個標頭在結構上答不了這個問題**：它們描述的是
**這一次 HTTP 交換**的性質 —— 有沒有命中邊緣快取、來源有沒有回應。
「線上是哪一版」是關於**來源持有什麼**的問題，
而任何一次成功的交換，對來源持有的是新是舊都是沉默的。

**做法**：判準只有一個，而且很便宜。

```
npm run build
curl -s https://<線上網域>/ > /tmp/live.html
diff /tmp/live.html dist/index.html && echo "線上 = 本機 dist"
```

- **相同** → 這一版真的在線上。
- **不同** → 先看 diff 的內容，不要先怪快取。
  差在整段 markup = 部署沒進去；差在一兩個雜湊檔名 = 資產部分上傳。
- 頁面不只一頁，所以**至少比對首頁 + 一頁你剛改到的**。

`_headers` / `_redirects` 這種**不在 HTML 裡**的東西，
比對的對象是 `curl -I` 的標頭本身對 `dist/_headers` 的內容，
不是狀態碼。

## 12. 跨 session、跨主機共用的資源：port、npx 快取、父目錄

**一句話**：本機模擬會**很有信心地給你錯的答案**，而且那個答案
長得完全像一份可信的結果。

**實例（固定 port 4321）**：
量 hero 對比要先把站跑起來，於是 `npm run dev`（Astro 預設 4321），
然後對 `http://localhost:4321/` 抓圖、逐字量測、得到一組漂亮的數字。

問題是**那個 port 已經被另一個 session 佔著**，跑的是 LEMONE。
Windows 允許重複 bind（不像 Linux 預設會 `EADDRINUSE` 擋下來），
所以第二個 dev server **沒有報錯**，它只是沒有拿到連線。
量到的是**LEMONE 的頁面**。

而它長得完全像一份可信的結果：有 hero、有標題、有副標、
逐字量測跑得出百分比、對比值落在合理範圍。**沒有任何一個環節會說話。**

**為什麼特別毒**：這一類錯誤不會產生「錯誤」。它產生的是
**一份格式正確、數字合理、關於錯的東西的報告**，
而報告的消費者（下一個 session、下一個人、下一份 PITFALLS 條目）
沒有辦法從報告本身看出它量錯了對象。

**同一形狀的其他共用資源**（`O:\電商站前台製作\` 底下不只一台主機在動）：

- **npx / npm 快取**：兩個 session 同時 `npx` 同一個工具，
  可能拿到對方正在寫入一半的快取項目。
- **父目錄**：`03_LOVISM_wt/` 之類的 worktree 是別台主機在動的，
  對它 `git status` 得到的是別人操作到一半的狀態。
- **`dist/`**：兩個 session 對同一個 repo `npm run build`，
  後跑完的覆蓋前一個，而前一個正在讀 `dist/` 做比對。

**做法**：

1. **不要用固定 port**。讓 OS 指派：
   ```
   npm run dev -- --port 0        # Astro 會印出實際拿到的 port
   ```
   然後**從輸出裡讀那個 port**，不要假設。
2. **量之前先確認你量的是誰**。抓一個只有這一站才有的字串
   （`identity.logoText`、`storageNamespace`）驗證頁面身分，
   再開始量。一行 `grep`，換掉整份報告作廢的風險。
3. **一個 repo 同時只有一個 session 在寫**。這是流程約定，
   不是技術保證 —— 但它是唯一有效的那個。
4. **看到「很乾淨」的結果先懷疑一次**。真實量測通常有毛邊；
   一份每個數字都剛好落在預期區間的報告，
   比一份有異常值的報告更值得回頭確認來源。

## 13. 第五族：格式正確、看起來可信、內容錯誤、而且不報錯

**一句話**：前十二條各自是一個故事。這一條是把其中好幾個歸成**同一族**，
因為它們的失敗形狀一模一樣 —— 產出的不是錯誤，是
**一份格式正確、數字合理、關於錯的東西的報告**。
而報告的消費者（下一個 session、下一個人、下一份 PITFALLS 條目）
**沒有辦法從報告本身看出它量錯了對象**。

前四族大致是：設定與平台的落差（#1 #3 #6）、
工具鏈會吃掉你的輸入（#4 #12 的一半）、
瀏覽器與資產的語意（#5 #8）、
稽核與量測之間的縫（#7 #9 #10）。
這一族與它們正交：**它問的不是「答案對不對」，是「你量的是不是你以為的東西」。**

### 七個實例

| 實例 | 看起來像 | 實際上是 |
| --- | --- | --- |
| **固定 port 4321 撞車**（#12） | 一份完整的 hero 逐字對比報告 | 量到的是另一個 session 跑的 LEMONE 頁面 |
| **`CF-Cache-Status: MISS`**（#11） | 「不是快取，所以是新的」 | 它只描述這一次交換，對來源持有的是新是舊完全沉默 |
| **靠顏色比對定位文案**（#9b） | 找到了標題的像素 | 找到的是照片裡那件**米色西裝** —— 它跟標題同色 |
| **Windows Store 的 `python` alias** | 指令跑完了，exit 0 | 它什麼都沒做。alias 在沒安裝時**靜默結束**，腳本的下一步拿到空檔案當輸入 |
| **截圖驗圖** | 版面壞了／圖沒出來 | 延遲載入還沒完成就截了圖，拍到的是**真空白但假結論** |
| **部署傳播中**（#11 方向一） | 新版沒上去 | 邊緣還在送舊版，或送一個 **17 bytes 的裸 404** —— 長得跟「少設 `not_found_handling`」一模一樣 |
| **`route.abort()` 擋掉資源** | 「沒有這張圖，版面就是這樣壞」 | 那個壞掉是**你自己造成的**，線上沒有這回事 |

七個裡沒有任何一個會丟出例外。這才是重點。

### 兩條反向的：報錯也不代表真的錯

上面七條講的是「綠燈不代表對」。反向同樣會咬人：

**一、`DIFFERS` + `MISS` 仍可能是邊緣節點沒更新。**
線上 HTML 與本機 `dist/` 逐位元比對（#11 的判準）回報不同，
第一直覺是「這一版沒部署成功」。但同一個判準在**傳播期間**會誠實地回報差異，
而那個差異三十秒後會自己消失。
**做法**：`DIFFERS` 之後**再比一次**，並看 diff 的形狀 ——
差在整段 markup 與差在一兩個雜湊檔名，是兩件不同的事。

**二、只比 HTML 會漏掉整個 CSS 層。**
一次改色的驗證裡，`#4e5f71` 改成 `#2c353d`，
兩者**同樣長度**，而且真正的改動在**樣式表裡**，不在 HTML。
逐位元比 HTML 得到「完全相同」，結論寫成「這一版沒上去」——
事實是它上去了，只是你比的那一層本來就不會變。
**做法**：改到樣式就要另外比 CSS，而且**比內容，不只比位元組數**。

### 一條判準：不會被量到的漂亮寫法

`var(--color-cta)` 比寫死 `#ae8543` 漂亮，這是對的，
而且 `audit:color` 的字面量禁令正是為此存在。

但要知道代價：**當一個值改成 `var()` 引用，它在那個位置就不再是一個「值」，
稽核也就悄悄停止量測那個 token 在那裡的表現。**
`src/lib/grounds.mjs` 的地面表存在的理由就是這個 ——
一個沒有被歸到任何 ground 的背景，是一個沒有人量的背景。

所以判準是：**把值換成引用的時候，順手問「現在還有誰在量它」。**
如果答案是「沒有」，那不是重構，那是把一個檢查換成一個註解。
`assertGroundsCover` 會對沒歸屬的 `-bg` 直接讓 build 失敗，
就是把這個問題從「記得問」變成「不問就過不了」。

### 一條下一層：比了 CSS，還要知道壓縮器會改寫什麼

決定去比 CSS 之後，還有一層。建置產物是**壓縮過**的，
而壓縮器會做等價改寫：

```
nth-child(2n+1)   →   nth-child(odd)
```

於是拿原始字串去 `grep` 產物，得到「找不到，所以規則沒進去」——
規則進去了，只是換了個等價寫法。同一族的其他改寫：
顏色 `#ffffff` → `#fff`、屬性簡寫合併、空白與最後一個分號消失、
scoped 屬性選擇器被折進去。

**做法**：比 CSS 的時候，比的對象是
**兩份都經過同一個壓縮器的產物**（改前 build 一次、改後 build 一次），
不是「原始碼字串 vs 產物」。
要找特定規則就搜**選擇器加宣告的語意**，不要搜你寫下的那串字。

**同一層的另一個**：Astro 的 `{...spread}` 會改變輸出的屬性集合。
一個條件式屬性寫成

```astro
{/* 看起來等價，不是 */}
<a href={link.href} {...external(link.href)}>
```

編譯期就無法確定這個元素有哪些屬性，於是 Astro 除了 `data-astro-cid-*`
之外**再補上 scope class** `class="astro-…"`。
實測：頁尾每一個欄位連結、每一個底欄連結都多了那個 class，
**每頁 322 bytes，每一站的每一頁**，而外觀完全沒有變。
零差異驗收就是這樣被一個「只是換個寫法」打掉的。

**做法**：要條件式屬性就**寫出來**，值給 `undefined` ——
Astro 不會輸出值為 `undefined` 的屬性，位元組與改之前完全相同。

```astro
<a href={link.href}
   target={isExternal(link.href) ? "_blank" : undefined}
   rel={isExternal(link.href) ? "noopener noreferrer" : undefined}>
```

### 再一個，而且它動到的是產物本身：不存在的旗標被靜默忽略

**這一條的重點不是旗標拼錯。** 是**旗標根本不存在，指令照跑**，
而且它跑的正是你以為自己避開的那個動作。

**實例**：想確認新增一個 `docs/*.md` 會不會被收進 `template.lock.json`，
於是跑

```
node scripts/write-template-lock.mjs --dry
```

`write-template-lock.mjs` **從來不讀 `process.argv`**。沒有 `--dry` 這個模式，
也沒有任何地方會說「我不認得這個參數」。它就是**照常把檔案寫出去**。

而它印出來的東西長這樣：

```
template.lock.json written: 75 locked file(s), 2 baseline file(s), at 51cdfa3.
```

**這一行同時是正確的、看起來像確認、而且掩蓋了損害。**
`75` 甚至就是當下要問的那個問題的正確答案（新檔沒有進鎖），
所以它讀起來完全像一次成功的乾跑。

真正發生的事：`template.commit` 被**重新蓋章**，
從「帶著這批變更的那個 commit」改成「只是替它蓋章的那個 commit」。
`locked` 的 75 個雜湊**一個都沒變**，所以

- `audit:template` 前後都是綠的 —— 它比雜湊，不比指標；
- 唯一會說話的是 `git diff`，而且只差兩行。

也就是說：這輪唯一用來辨識自己的那個指標被改掉了，
四道稽核沒有一道會發現，輸出訊息還在恭喜你。

**做法**：

1. **你發明的旗標不是旗標。** 相信一個模式存在之前，先確認腳本真的讀 `argv`
   （`grep argv scripts/<name>.mjs`）。會寫檔的產生器**應該拒絕**不認得的參數，
   而不是忽略它 —— 忽略與支援在輸出上長得一模一樣。
2. **「這樣會不會改到東西」要問 git，不要問工具。**
   照跑，然後 `git diff` / `git status`；或先複製一份 repo 再跑。
   工具自己的輸出回答不了「你剛剛改了什麼」。
3. **指標型的欄位特別危險** —— 它不影響任何檢查，所以沒有檢查會攔它。
   內容錯了會有人量，來源錯了沒有人量。

## 14. 鎖是兩層的：`core` 永遠鎖，`presentation` 由店宣告解鎖

`template.lock.json` 的每一筆都帶 `tier`。這不是「母版 vs 店」的所有權之分，
而是**「錢與會員邏輯」vs「頁面版面」**之分 —— 兩邊都還是母版的檔，
`presentation` 說的是「店**可以**接手」，不是「店已經擁有」。

| tier | 內容 | 稽核行為 |
| --- | --- | --- |
| `core` | `src/scripts/**`、`src/lib/**`、`BaseLayout.astro`、`BeaconBoot.astro`、`scripts/**`、`astro.config.ts`、`tsconfig.json`、`.gitignore`、`docs/PITFALLS.md` | 永遠逐位元組。店**不能**宣告解鎖。 |
| `presentation` | `src/pages/**`、`src/routes/**`、`src/components/**`、`src/styles/**` | 預設一樣逐位元組；店在 `brand/unlock.ts` 列名後，該檔改為只印報告。 |

分界線在 `scripts/template-lock.mjs` 的 `CORE` / `PRESENTATION` 兩個陣列。
`CORE` 先比，所以 `src/components/common/BeaconBoot.astro`（明列）贏過
`src/components/`（目錄）。

**三個容易踩的地方**

1. **沒歸類的路徑會 throw，不會有預設值。**
   新增 `src/utils/` 這種既不在 `CORE` 也不在 `PRESENTATION` 的目錄，
   `npm run template:lock` 直接失敗。這是刻意的：兩種預設都錯 ——
   預設 core 會讓新頁面不可客製而沒人發現，預設 presentation 會讓下一個
   `src/lib/` 的鄰居變成可解鎖而**更沒人發現**。同 `assertGroundsCover`。

2. **`brand/unlock.ts` 裡寫錯路徑是硬失敗，不是靜默無效。**
   打錯字、寫到 core 檔、寫到鎖裡沒有的路徑 —— 三種都讓 `audit:template` 直接
   throw 並指名該行。理由：一行「沒生效的宣告」等於店以為那頁是自己的，
   直到某次改動以 drift 失敗，而那則訊息完全不會提到 `brand/unlock.ts`。

3. **舊格式的 lock 會被拒絕，不會被猜。**
   拆層前的 `locked` 是「路徑 → 雜湊字串」。腳本與 lock 是**一起**同步的，
   單獨帶其中一半過來就是同步做壞了；兩種猜法各錯一半的檔，所以直接報錯要你
   重新取一份。

**解鎖不是免費的。** 解掉一頁，母版之後對那頁的修正就不再到達這家店。
`audit:template` 每次都會印出解鎖清單，母版端的 `npm run template:report`
則告訴你母版有而這家店沒有的東西。這個「有人知道」的機制就是解鎖的代價本身。

## 15. `scripts/dom-contract.mjs`：拆鎖之後，版面與腳本之間唯一的警報

拆鎖之前這件事不存在：腳本碰到的每一頁都逐位元組等於母版，
「`/checkout` 還有沒有 `[data-confirm]`？」的答案永遠是「有，否則 `audit:template`
早就紅了」。可以宣告解鎖之後，店拿到一頁的第一件事就是重畫它，
而 `src/scripts/` 的三千多行全都綁在那份 markup 上。

**掉一個 hook 的失敗長什麼樣子**：build 綠、頁面正常渲染、console 不報錯、
截圖看不出來 —— 只是結帳按鈕不會有反應。而母版四家有資料的店裡
carts 35 筆、orders 0、customers 0：**沒有任何流量會發現這件事**。
`scripts/dom-contract.mjs` 加上 `tests/dom-contract.test.mjs` 就是全部的警報。

宣告分五類，每一條都必須落在其中一類，否則測試紅：

- `CONTRACT` —— 頁面**伺服器端就要有**的 selector，按 script × 頁面分組，
  每條附 `src/scripts/` 的來源行號。頁面不存在（flag 關掉）或 `gate` 不在時整組跳過。
- `RUNTIME` —— 腳本自己 `createElement` 出來的節點上的 selector。重畫拿不掉，
  因為腳本沒跑之前它們根本不存在。
- `OPTIONAL` —— 母版**刻意不渲染**、腳本用 `if (...)` 保護的 hook。
  entry 必須指名那個 guard 運算式，測試會回頭確認它真的在原始碼裡 ——
  否則這一類會變成「把測試弄綠」的垃圾桶。
- `DEAD` —— 綁在任何頁面都沒有的 markup 上。
- `TEMPLATED` —— 由變數組出來的 selector，附上它可能展開成的字串。

**⚠️ 抽出來之後一定要逐條回頭核對。** 這不是儀式：第一次跑 presence 檢查就抓到
兩件 grep 給不出來的事 —— `[data-clear-cart]`（cart.ts:893）綁在整個 repo 都沒有的
markup 上，`[data-promo-chip-amount]`（checkout.ts:347）讀的是 checkout 頁**故意移除**
的元素。regex 會把這兩條都當成正常的合約條目。

覆蓋率是雙向的：測試會重新掃四支腳本，任何**沒被宣告**的 selector 也會紅。
所以這份清單不會悄悄落後於程式碼 —— 在腳本裡加一個 selector，
就是在 review 裡被迫決定它屬於哪一類。

## 16. 跑馬燈用 `margin`，不要用 `gap`

無限跑馬燈的標準做法是把內容複製一份、動畫跑 `translate3d(-50%)`。
用 `gap` 排 tile 的話，軌道實際是 **12 個 tile + 11 個 gap** ——
`-50%` 落在「六個 tile + 五個半 gap」的位置，短了半個 gap，
於是接縫每一圈跳一次（thesix 第三輪：8px 的 gap，跳 4px）。

```css
/* 錯：track 是 12 tiles + 11 gaps，-50% 對不上 */
.ig__track { display: flex; gap: 8px; }

/* 對：每個 tile 都貢獻 tile + 8px，-50% 剛好是六個 */
.ig__cell { flex: none; margin-inline-end: 8px; }
```

一般化的說法：**任何靠 `-50%` 對齊的循環，元素之間的間距必須算進「每個元素」，
不能算進「元素之間」。** `gap` 天生比元素數少一個，永遠差半個間距。

同一個道理反過來用在別處：`PageHero` 的 `.hero-copy` 也是 `margin` 不是 `gap`，
理由不同 —— 那裡的 eyebrow / lead / 麵包屑都是選用的，`gap` 會把一個「不存在的
子元素」也排出間距，於是只給 title 的 hero 會多一段沒人放東西的空白。
